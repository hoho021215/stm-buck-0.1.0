# STM32 동기식 벅 컨버터 0.1.0

NUCLEO-F303ZE에서 **같은 펌웨어로 제어 기능 한 가지씩을 켜고 끄며 출력 변화를 측정**하는 실험용 모듈입니다. 목표는 30 V 입력, 15 V / 1 A 출력, 50 kHz PWM입니다. 전압 루프가 듀티를 계산하고 인덕터 전류로 듀티 상한을 조절합니다. 전류 지령을 추종하는 내부 전류 루프는 이번 버전의 비교 항목에 포함하지 않았습니다.

현재 생성한 CubeIDE 프로젝트에 사용자 모듈을 추가합니다. 파일명, 줄 번호, 생성된 코드의 `USER CODE` 위치는 [CubeIDE 적용 안내](INTEGRATION_KO.md)에 있습니다. 기능 전환과 측정은 기존 ADC·DMA·TIM1을 사용합니다.

**[설계 변경·증상별 대응 가이드](DESIGN_TUNING_KO.md)**에서 정격 부하 전류 제한, 느린 기동, 게이트·ADC 타이밍, PI와 보호값, 목표전압 변경, A/B 실험에 필요한 수정 위치와 검증 방법을 찾을 수 있습니다.

PC에서 인덕터·커패시터 실측값을 넣고 피드포워드 ON/OFF 파형을 비교할 수 있습니다. [시뮬레이션 설치·실행 가이드](SIMULATION_KO.md)

## 이번 버전에서 달라진 점

0.0.2의 출력 감시 및 보호를 유지하고 기동 시 선택하는 세 가지 기능과 정상 운전 중 50 ms 측정을 추가했습니다. 기존 제어식에 해당하는 기본 선택값은 **7**입니다. 디버거로 입력한 기동·정지 명령은 펌웨어가 실제로 읽은 경우에 소비합니다. [0.0.2 기준 커밋](https://github.com/hoho021215/stm-buck-0.0.2/tree/c8b6320a3db2230ddb80b11abbcf6bd11fab6271)

| ON/OFF 항목 | ON일 때 | 해당 기능만 OFF로 비교할 때 |
|---|---|---|
| 실측 입력전압 피드포워드 (값 1) | 기준전압을 매 주기 측정한 입력전압으로 나눠 기본 듀티를 계산 | **7 ↔ 6**. OFF는 분모를 공칭 30 V로 고정합니다. 두 조건 모두 정격에서 기본 듀티가 0.5이므로 입력전압 변동 보상의 효과를 비교할 수 있습니다. |
| 듀티 포화에 대한 적분 보정 (값 2) | 요청 듀티와 실제 적용한 듀티의 차이를 적분기에 되먹임 | **7 ↔ 5**. OFF에서도 적분기 자체의 상·하한은 유지됩니다. 듀티 제한에 걸렸다가 풀리는 조건에서 회복 거동을 비교합니다. |
| 정상 운전 중 듀티 상승률 제한 (값 4) | 듀티 증가량을 초당 1.0, 50 kHz 기준 한 주기당 0.00002로 제한 | **7 ↔ 3**. 약 1초의 기동 확인을 통과한 후에만 차이가 생깁니다. 부하 변화 뒤 전압 강하와 표본 전류 최대값을 함께 봅니다. |

`buck_feature_request`에 켤 항목의 값을 더해 **0~7**을 씁니다. 0은 세 항목을 모두 끄는 값입니다. 어떤 조합에서도 소프트스타트, 기동 중 듀티 상승 제한, 전류에 따른 듀티 상한, 과전류·역전류·과전압·저전압 차단, ADC·시간 감시가 적용됩니다. 0.0.2와 같이 전력단은 기본 `BUCK_BOARD_VERIFIED=0`으로 기동이 차단됩니다. [기능 비트 정의](Core/Inc/buck_app.h#L12) · [제어식](Core/Src/buck_app.c#L231) · [보드 설정](Core/Inc/buck_board.h#L11)

**[기능 ON/OFF 표와 소스 줄 번호](FEATURE_SWITCHES_KO.md)**에서 디버거에 쓸 값과 각 기능의 헤더 정의·기동 처리·제어식을 바로 찾을 수 있습니다.

## CubeIDE에서 두 조건 비교하기

1. 처음 통합할 때는 기본 기동 차단 상태로 빌드하고 ADC 입력 순서와 영점, EN과 두 게이트 파형, 보호 동작을 먼저 확인합니다. 다음 절차는 **기동 검증이 끝난 보드**를 전제로 합니다. Debug와 Release 중 한 구성(권장 `-O2`, fast-math 꺼짐)을 정하고 A/B 모두 같은 바이너리로 진행합니다.
2. **Live Expressions**에 `buck_feature_request`, `buck_arm_request`, `buck_debug`, `buck_measure_request`, `buck_measurement`를 추가합니다. 전력단 운전과 측정 중에는 CPU가 계속 실행되어야 하므로 중단점이나 일시정지를 사용하지 않습니다.
3. **A 조건**은 `buck_debug.state == 0`(정지) 및 `buck_debug.calibrated == 1`에서 `buck_feature_request = 7`을 먼저 씁니다. 이어 `buck_arm_request = 1`을 한 번 씁니다. 명령이 0으로 소비됐는지, `buck_debug.active_features == 7`인지, `buck_debug.monitoring == 1`로 정상 기동 검사를 통과했는지 확인합니다.
4. 비교할 입력·부하 조건을 가하고 `buck_measure_request = 1`을 한 번 씁니다. `buck_measurement.status == 2`이고 `samples == 2500`이 되면 결과와 `active_features`를 기록합니다. 다음 유효한 요청이 들어올 때까지 완료 결과가 보존됩니다.
5. **B 조건**으로 바꿀 때는 `buck_arm_request = 2`로 정지하고 정지 상태와 명령 소비를 확인합니다. 출력이 기동 허용 범위(0.5 V 이하)로 내려온 뒤, 비교할 값 6·5·3 중 하나를 쓰고 3~4단계를 반복합니다. 운전 중에 기능 값을 써도 적용 중인 조합은 유지됩니다. 원인 확인이 필요한 고장은 첫 고장 기록 `buck_fault_snapshot`에 남습니다.

재현성을 높이려면 같은 입력전압, 부하의 크기·변화율, 프로브와 측정 시간을 사용하세요. 피드포워드 효과는 **입력전압을 바꾸고 부하를 고정**하면 관찰하기 쉽습니다. 듀티 제한 비교에는 **입력전압을 고정하고 같은 부하 패턴**을 사용하세요. 예를 들어 정격 범위 안에서 100 Hz 주기 부하를 안정적으로 반복하면 50 ms에 다섯 주기가 들어갑니다. 단발 부하 스텝의 정착 시간은 전자부하의 트리거와 오실로스코프를 동기화해 확인하세요. 디버거로 쓰는 명령의 시점은 부하 스텝과 동기화되어 있지 않습니다.

## 50 ms 측정 결과 읽기

ADC 콜백에서 정상 운전 표본 2,500개를 모읍니다. 마지막 표본의 시간 검사를 마치고 다음 정상 콜백에서 완료 상태를 공개합니다. 완료값을 읽을 때는 `status = 2`를 확인하세요. 0은 대기, 1은 수집 중, 3은 중단입니다. 정지·고장 등으로 중단된 창은 A/B 수치에서 제외하고 중단 자체를 실험 결과로 기록합니다. 운전 준비 전이나 수집 도중 들어온 중복 요청은 `rejected_requests`에서 확인할 수 있습니다.

| `buck_measurement` 필드 | 의미 |
|---|---|
| `active_features`, `samples` | 이번 기록에 실제 적용한 조합과 표본 수 |
| `vout_min_v`, `vout_max_v` | 창 안의 출력전압 최솟값과 최댓값(V). 15 V 기준 강하는 `max(0, 15 − 최솟값)`, 오버슈트는 `max(0, 최댓값 − 15)`입니다. |
| `mae_v` | 평균 절대 전압오차. 각 표본에서 15 V와의 차이의 절댓값을 취해 평균한 값(V) |
| `peak_abs_il_a` | 같은 창에서 ADC가 관측한 인덕터 전류 절댓값의 최댓값(A) |
| `duty_min`, `duty_max` | 제어기가 명령한 듀티 범위(0~1) |

주기당 고정 위상의 ADC 표본을 사용하므로 스위칭 리플의 피크와 실제 게이트 펄스 폭은 오실로스코프로 측정하세요. 동일 파형을 여러 번 반복하고 각 결과의 범위도 비교하면 측정 편차와 기능별 차이를 구분하기 쉽습니다. [결과 구조체](Core/Inc/buck_measurement.h#L16) · [측정 코드](Core/Src/buck_measurement.c#L25)

## 검증

Linux/WSL에서 Python 3, Git, GCC로 `python3 tests/run_host_tests.py`를 실행합니다. 첫 실행은 스크립트에 고정한 ST HAL·CMSIS 및 Arm CMSIS 버전을 내려받습니다. `--sanitize`는 추가 런타임 검사를 수행합니다. ARM GNU 도구체인을 설치했다면 `--arm`으로 Cortex-M4F용 객체 컴파일도 실행할 수 있습니다. `tests/`는 PC 검사용 폴더입니다.

게시 전 호스트에서 앱 시나리오 32개, 하드웨어 설정 검사 40개, 출력 감시와 50 ms 측정 시험(반복·완료·극값·중단·거부), 기본 기동 차단을 통과했습니다. 기능별 비교는 동일한 ADC 입력을 주입해 듀티·적분기·차단 동작을 확인했습니다. ASan/UBSan은 출력 감시와 측정 모듈, UBSan은 앱과 하드웨어 설정 검사에 적용했습니다. GCC 14.2.1로 제품 모듈 4개를 Cortex-M4F hard-float 객체로 컴파일했습니다. 사용자 프로젝트 전체 ELF 링크, 보드의 실제 ISR 실행 시간, 출력전압·전류의 물리적 개선량은 실측 대상입니다.
